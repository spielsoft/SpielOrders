## Decision

SpielOrders uses a native macOS list and persistent detail pane in which the selected record is always editable. This document defines product behavior, not a web-widget layout or a framework-specific implementation.

### Window and navigation

SpielOrders is a macOS-native, single-window desktop application with one active SpielOrder Package. Package actions belong in the standard menu bar, not a custom toolbar dropdown. File exposes New Package…, Open Package…, Reload Package, a New item named for the current destination, Set Up Agent Guidance…, and Close Window, and Save for the expert document editor; the Package menu exposes diagnosis and Show in Finder. The New item and ⌘N create a record of the kind the current destination shows (New Order, New Vendor, New Orderer, New Institution, New Project) and are disabled where nothing can be created; Edit → Find (⌘F) places the cursor in the current destination's search field and is disabled where there is none. Menus, buttons, and messages name actions by what the owner is doing rather than by implementation. File → Open Recent lists recently opened Packages by name, most recent first, and the welcome view lists the same recent Packages beside its actions; choosing one opens it through the same guarded load as Open Package, and a recent Package that is missing or no longer accessible says so and can be removed from the list. Agent Ready (Set Up Agent Guidance…) is available without an open Package, including from the welcome view beside Open Package and New Package, and chooses its own existing directory without saving, discarding, or replacing the current editor. The window title names the current destination (Orders, Vendors, Orderers, Institutions, Projects, or Package README) and its subtitle names the active Package, whose folder the proxy icon and path menu still represent; a page does not repeat its destination as an in-pane heading. An unsaved record never receives a fabricated filesystem location. Orders, Vendors, Orderers, Institutions, Projects, and the Package `README.md` are destinations in a collapsible sidebar at the window's leading edge, not a toolbar control, and appear only while a Package is open. Orderers, Institutions, and Projects each show a table of their values, used by an Order or not, with the number of Orders using each; Projects list each Project's Order Groups beneath it. An Order Group belongs to its Project, and two Projects may each have a group of the same name. Each of these tables, and Vendors, adds a value with a + bar (in Projects, a group of the selected Project, otherwise a Project), renames a value in place by double-click, and offers a right-click Delete… that asks for a replacement when the value is used and Merge N … for several selected rows that asks which spelling to keep, such as AbC over Ab_C. Each sheet states how many Orders change, and every affected Order follows the change; renaming onto an existing value offers a merge. There is no real browser product surface.

The window has three columns: the destination sidebar, the record table, and the detail. The table is ordinary content, not a sidebar, and keeps the most width. The leading sidebar control and View → Show/Hide Sidebar hide only the destinations, preserving the selected content; View also exposes the destinations. Search stays above the list it filters, and creation sits below it. The default window fits the dense Orders grid and detail; narrower detail forms scroll and row tables scroll horizontally. The visual language follows native macOS conventions. The expert document editor exposes a clearly labeled Save action, never a share-like titlebar icon. Package initialization uses an attached setup form after its folder picker detaches.

Closing the window and quitting the application share dirty-draft protection and settle owned work before proceeding. A cancelled leave preserves a usable editor. An approved Close of an active Package releases it and returns the window to its welcome view. Close from the welcome view quits SpielOrders. Quit ends the application through AppKit's termination protocol. A successful Open replaces the remembered Package, and an approved Close of a loaded Package forgets it. A failed or interrupted restore preserves its remembered target through Quit. Launch reopens the remembered Package, and a Package opened from Finder takes precedence. The window shows loading, not the welcome view, until that Package resolves.

A deletion that replaces values in Orders starts without a replacement selected. The owner
explicitly chooses a replacement or None. Delete remains unavailable until the library's
plan and affected-Order count for that choice are ready.

### Orders table and lookup

The primary Orders view is a dense, informative grid designed for hundreds or thousands of Orders. The list and persistent detail share the window's content area. A left-aligned line above the grid reports **“N of M Orders”**, where the count includes damaged placeholders. Selection shows the record's editable detail in that pane; there is no separate Edit mode. Double-click, Return, or contextual Open focuses that detail without reloading it or asking to discard input. Filtering or hiding the list retains the selected content and input.

The default visible columns are Date, Status, Order Title, Vendor, and Orderer. Right-clicking the header opens a checkbox menu containing every available column; optional columns include Institution, Project, Order Group, Directory Name, Currency, Order ID, and Total. Total is not visible by default. Column visibility, order, and widths are app preferences and persist independently of Package data.

Ordinary search live-filters the grid and retains its current sort. A filter button beside the search field opens a **Search In** menu: All Fields by default, then each searchable Order and Item fact whether or not its column is shown, and, after a separator, **Folder Contents (Spotlight)**. The same menu holds **Match Case**; there is no separate case button. Folder Contents keeps the query and the grid: the grid shows the Orders whose facts or Supporting Material match, the latter through OS-native search, and the selected Order's detail lists its matched files, each of which can be opened or revealed. Match Case does not apply to Supporting Material. Vendors offer the same menu over Vendor facts, without Folder Contents. The library decides what matches in every scope. Structured-filter UI remains deliberately undefined for later user testing and post-MVP work.

Damaged Order placeholders appear only in the unfiltered grid with one diagnostic marker, not a fabricated Status or a fully red row. Their detail shows the trusted directory name and diagnosis; damaged Orders do not participate in either search mode.

### Selection, removal, and Finder

Order detail contains ordinary facts, Directory Name, Items and their Total, the Order's `README.md` as an editable text area, and Show in Finder. Statuses use their friendly labels. Displayed money shows two decimals, or every decimal a finer stored amount has, in the system's currency style when the Order's currency is an ISO code and as a plain number otherwise, without recalculating library values; a cell being edited shows its amount exactly as typed. Supporting Material remains a Finder-owned opaque directory tree; the application does not embed a browser, upload surface, or inventory.

The row context menu contains Open, Show in Finder, Align Directory Name, Remove Order, and a visually separated Move to Trash action. The application Order menu exposes the same appropriate commands. Remove Order, including the ordinary macOS Delete key, commits without a confirmation because it is recoverable, and Edit → Undo restores the removed Order through the library. Move to Trash and Align Directory Name each show the exact planned operations in a bounded, scrollable review sheet before committing. A Trash handoff that fails after removal leaves the Order recoverable and is reported differently from a completed Trash move. A New Order plus action sits at the bottom of the Orders list; removal remains an explicit command rather than a list-footer minus button. The Order detail's heading is the Order Title with a one-line summary beneath it (status, date, vendor), not a second copy of the Title field. The directory name sits in a small Folder row with Show in Finder. **Align Directory Name** lives in the Order menu and the row context menu; the detail offers it beside the Folder row only when the library reports that the directory name differs from the name the Order's facts project.

### Order and Vendor editing

Existing Orders and Vendors automatically persist a complete guarded draft when a field or row edit ends. Selecting another record, valid navigation, Close, and Quit finish those edits without a routine Save/Don’t Save question. A brief save interval gates mutation and preserves the next intended action and focus; newer accepted input is never overwritten by an older save result. Undo and Redo apply inverse values through the same guarded backend mutation path, including after focus changes. They do not introduce a separate persistence or merge policy. Ordinary editing keeps one window-wide Undo history that survives selecting another record, so Edit → Undo names and reverses the most recent ordinary edit, removal, or other undoable change. Expert raw-JSON and replacement-JSON editors each keep a separate document-local Undo history for their current draft; those edits never enter the ordinary window history.

A new Order starts with Title New Order, selected so typing replaces it, and the library's Date and Status defaults. It remains a draft until Create creates it; Cancel discards the uncreated draft. A new Vendor, including one created from an Order, follows the same staging boundary and starts as New Vendor, numbered past any Name the Package already uses. Leaving an unwritten new record can ask to discard it but never silently creates it.

Status is an ordinary dropdown containing only the five domain statuses. Selecting Ordered applies the library's Date Ordered behavior, and a later explicit date edit remains possible. Date Ordered is a native date field with a calendar pop-up rather than free text, and the grid shows dates in the system's short date style; the library still receives its own date spelling and validates it. An Order without a date shows an empty field that can be cleared again, and a stored date the calendar cannot represent is shown as stored with its problem until a valid date is chosen. Vendor, Orderer, Ordering Institution, Project, and Order Group use one chooser: a field that completes inline and filters its list as you type, and accepts only an existing value or, where the field is optional, none; there is no separate popover. Order Group lists only the current Project's groups. When the typed text matches nothing, the list's last item reads New Orderer “text”… (named for the field) and adds that value after a confirmation; New Vendor opens the Vendor sheet with the name filled in, preserves the Order draft, and selects the result. Window-specific confirmations and folder panels use asynchronous attached sheets, including questions about the active Vendor sheet.


Order Items are edited as a plain spreadsheet in the detail pane, using the same restrained row-and-column language as the main Orders table rather than separate rounded input controls. Catalog Number precedes Description; Description receives most of the width, while Quantity and Unit Price remain compact numeric columns without increment/decrement steppers. Double-click or Return begins editing, Tab advances, drag changes order, and conventional plus/minus controls appear beneath this Items table. The Items table, like a Vendor's Contacts, grows with its rows to a limit and then scrolls, and an empty one quietly says No Items. Existing-record row changes use the same automatic commit and inverse Undo path; new-record changes stay staged until the record is created. The library's calculated Order Total belongs in the table footer. An Item's optional multiline Notes appear as an Items column that is hidden by default and chosen from the header's right-click column menu; rows keep one height, a row with notes shows a small indicator, and Notes are edited in a multiline popover. Notes never affect totals.

Validation comes from the library when committing, not a preliminary modal or a high-level GUI validator. Invalid, stale, or failed writes retain input in the detail with visible Not Saved and inline field or item problems. Navigation does not discard that input; retry, explicit revert, or guarded reopen provide recovery. Committed warnings remain committed and do not invite duplicate writes. Successful operations are silent; nothing reports that a save, search, creation, or removal worked. There is no message footer. A problem is shown where it occurs, in the native way: a field or Item cell with a problem is drawn in red with a small warning symbol, whose tooltip states the problem and whose popover adds the actions that fix it (Retry, Revert, Reload Package, Details). A record that is Not Saved, or saved with warnings, shows that state as a symbol in its heading with the same popover. Package and listing warnings appear as a warning symbol on the affected sidebar destination, whose popover offers Details and Diagnose, and a search provider problem appears as a symbol in the search field. A consequence the owner should notice, such as a cleared Order Group, marks the affected field the same way until the next edit. Only an action the owner started that fails with nowhere to show it, such as lost Package access, a failed Show in Finder, Align, or Trash, uses an alert sheet. A problem's tooltip and popover state it in plain language for the field it marks ("Quantity must be a number"), chosen from the library's problem code and field, while Details keeps the library's own wording. Details always opens a scrollable sheet with the library result and each entry's severity, code, message, location, field, reason, and evidence, and a nested Vendor's outcome stays separate from its Order's. Package and Order `README.md` surfaces are always-editable plain-text Markdown editors with lightweight syntax highlighting, no rendered preview, and no formatting toolbar. They save automatically through the library's guarded README save when typing pauses or the text loses focus, with no Save button; a failed save keeps the text with Not Saved and offers Retry or Revert, and navigation, Close, and Quit finish a pending save as they do for record fields. Raw correction and repair retain their explicit confirmation boundaries.

Vendors use the same list and always-editable detail as Orders. The Vendor detail's heading is the Vendor name with a one-line summary beneath it (how many Orders use the Vendor, and Hidden when it is hidden) and a small control beside the name that hides or shows the Vendor; the Vendors table's row menu offers the same Hide or Show. Detail retains Contacts and notices, and lists the Vendor's Orders compactly with their Title, date, Status, and Total; double-click or Return opens one. Shared Vendor facts remain live; guarded domain operations stay in the Rust core.

### Damage and repair

Double-clicking a Damaged Order opens a separate diagnostic workspace. Each diagnosis shows evidence and only the allowed explicit actions. The user selects one action, supplies its facts, reviews the exact planned change in a bounded, scrollable sheet, applies it, and the Rust core revalidates. There is no generic Fix or Fix All.

The GUI has one deliberate architectural escape hatch: the diagnostic workspace may directly edit and write raw managed JSON, bypassing the Rust library and CLI mutation APIs, and then ask the Rust core to revalidate. This is not a core repair action, does not attempt partial salvage, and has no GUI-level validity gate. If the written text is still invalid, the Order remains damaged. The exception exists for expert recovery and is expected to be rarely used; all ordinary reads and mutations continue through the typed Rust core.

### Frontend architecture

The desktop uses SwiftUI with AppKit integration for controls and native behavior that need it. Pure SwiftUI is not a goal at the expense of native table editing, keyboard behavior, undo, menus, or termination. There is no browser product and no shared frontend package with SpielGantt.

Swift directly links the Rust library and calls its generated C interface. [Effect and adapter boundaries](../../../../docs/architecture/boundaries.md) owns the division of responsibilities; the [implementation roadmap](../../../roadmaps/spielorders-implementation-roadmap.md) sequences native integration and deployment. Swift manages presentation and editor sessions, not Package rules. A future platform-independent service remains possible but is not an MVP requirement.

Use native controls and conventions rather than reproducing web-component internals. Concrete visual choices are evaluated in the real macOS application against the behavior above. [Desktop acceptance](../../../../docs/development/desktop-acceptance.md) governs validation.
